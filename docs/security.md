# Security

This document describes the controls in the code, how they are tested, and what is not covered.

## Threat model

| Actor                           | Can                                                  | Must not be able to                                                       |
| ------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| Anonymous visitor               | Read published content, search, feeds, theme CSS     | See drafts, scheduled posts, admin data, private files, the database      |
| Author                          | Write and edit own posts, save drafts, upload images | Publish, feature, edit others' posts, manage themes or users              |
| Editor                          | Publish any post and page, manage taxonomy and media | Manage themes, users, settings, or the audit log                          |
| Administrator                   | Everything in the CMS                                | Run code from a theme, read secrets, escape the theme or data directories |
| Theme author (untrusted upload) | Supply a ZIP of data files                           | Execute code, read files outside the theme, change content                |

## Controls

### Authentication

- Passwords are hashed with bcrypt (cost 12, `src/lib/auth/password.ts`). Unknown emails still run a comparison, so response time does not reveal which accounts exist.
- Login is limited to 5 attempts per 15 minutes per email and client address. The limit is in memory (`src/lib/auth/rate-limit.ts`).
- Sessions use 32 random bytes in an `HttpOnly`, `SameSite=Lax` cookie, `Secure` in production. The database stores only the SHA-256 hash of the token. Sessions last 7 days.
- Sign-out deletes the session row.
- Failed logins are recorded in the audit log without the password.

### Authorization

- Every mutation calls `requirePermission()` or `assertPermission()` on the server (`src/lib/auth/session.ts`). The permission matrix is in `src/lib/auth/permissions.ts`.
- Admin pages redirect anonymous visitors to sign-in. Hidden buttons are not the control; the actions reject the call anyway.
- Authors are limited to their own posts at the query level as well as in the mutation.
- `/api/v1/themes` returns 401 to anonymous visitors and 403 to non-administrators, with no data in either case.

### CSRF

- Server Actions (all admin forms) are protected by Next.js, which rejects requests whose `Origin` does not match the host.
- Cookies are `SameSite=Lax`, so cross-site POST requests do not carry the session.
- No Route Handler accepts POST. All writes go through Server Actions, and GET handlers do not change state.

### Input validation and output encoding

- All inputs pass Zod schemas (`src/lib/validation/schemas.ts`) before use.
- Rich text is sanitized on write with an allow-list (`src/lib/security/sanitize.ts`): no scripts, no event attributes, no `javascript:`, `data:` or `iframe`. Links receive `rel="noopener noreferrer nofollow"`.
- Theme output uses React escaping. The only raw HTML insertion is the sanitized post and page body. Tests check that a script in a post is removed before it is stored and before it renders.
- Search queries and titles are escaped in the page (tested).
- SQL is never built from strings, except the constant-structure `VACUUM INTO` in the backup script, whose path is generated by the script and quote-escaped.

### Uploads

Theme ZIPs (`src/lib/themes/zip.ts`):

- 5 MB upload limit. The check runs before the file is read.
- Magic bytes must be `PK\x03\x04`.
- At most 300 entries, 3 MB per file, 15 MB in total, compression ratio at most 100:1.
- Names with `..`, absolute paths, backslashes, NUL bytes, hidden segments, or case-only duplicates are rejected.
- Symbolic links are rejected from the ZIP central directory and again on disk after extraction.
- Only the allow-listed files are accepted (`isAllowedThemeFile` in `contract.ts`).
- Extraction goes to a staging folder inside the themes directory. Nothing reaches the live folder until validation passes.

Theme contents (`src/lib/themes/validate.ts`):

- The manifest is validated with Zod in strict mode.
- Templates may use only the registry components, with props validated.
- Stylesheets are scanned for `@import`, `expression()`, `behavior`, `-moz-binding`, `javascript:`, and HTML. `url()` may refer only to existing theme assets.
- Tokens and text settings that become CSS values use a strict character set. Braces, semicolons and `url(` are refused, so a value cannot break out of its declaration.

Media (`src/lib/media.ts`):

- The file type is read from the first bytes. The browser's MIME type and filename are ignored.
- SVG is refused, since it can contain script. So are HTML and executables with an image extension.
- Files are stored under a random name in `data/media/`, served by database id through a route that rejects other input, and sent with `nosniff` and a restrictive CSP.
- Images are limited to 6000 pixels per side and 5 MB.

### File access

- `data/` is outside `public/`. Next.js serves only `public/` statically, and nothing from `data/` is reachable except through the routes below.
- Theme assets: the route accepts only `styles.css` and `assets/<file>` with an allow-listed extension, from an installed theme and the exact version. `theme.json`, templates, dotfiles and `..` segments return 404 (tested).
- Media: the id must match a database row, and the stored filename is basename-only.

### Preview

- A preview link carries an HMAC-SHA256 signed token that expires after 10 minutes. It names one theme and grants read access to that rendering only. It cannot change settings, activate a theme, or read admin data. The signing secret is `PREVIEW_SECRET`, which production requires (at least 32 characters).
- Preview pages are `noindex`.

### Theme execution

- Themes cannot run JavaScript on the server or in the browser.
- The application uses no `eval`, no `new Function`, and no dynamic import of theme files. Confirm with `grep -rn "eval(\|new Function\|import(" src` — it should find nothing from theme code.

### Headers

Set in `next.config.ts` for all routes:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` disabling camera, microphone and geolocation
- `Strict-Transport-Security` (effective over HTTPS)

Theme assets and media add their own `Content-Security-Policy` with `default-src 'none'`.

### Secrets and errors

- Secrets come from the environment. `.env` and `data/` are git-ignored.
- Error messages shown to users come from a whitelist of error classes (`src/lib/errors.ts`). Other errors return a generic message, and the detail goes to the server log.
- Theme validation messages use relative paths only, never server paths (tested).

### Audit

Administrative actions write `AuditLog` rows: content, taxonomy, media, users, settings, theme installs, updates, activations, rollbacks, uninstalls, previews, and failed logins. The detail field never includes passwords, tokens or file paths. The admin screen shows the 200 most recent entries.

## Test coverage for these controls

- `tests/unit/zip.test.ts`: traversal, absolute paths, backslashes, symlinks, hidden files, duplicate names, executable types, archive bomb by ratio, oversize entries, too many entries.
- `tests/unit/validate.test.ts`: manifest errors, missing and unknown templates, invalid component props, forbidden CSS, `url()` checks, token injection, SVG, symlinks on disk, no absolute paths in messages.
- `tests/unit/security.test.ts`: sanitizer, slugs, preview token forgery and expiry, setting value injection, image signatures, password hashing, rate limit, role matrix.
- `tests/integration/access-and-media.test.ts`: server-side permission checks, author and editor limits, media upload checks, asset route traversal and hidden-file requests.
- `tests/integration/theme-switching.test.ts`: content unchanged across switches, activation refused for tampered themes, uninstall protection, malicious upload rejection, update backups.
- `tests/e2e/critical-flows.spec.ts`: anonymous redirect, wrong password, publish to public site with a script stripped, rejected archive, preview without activation, activate and roll back, upload, SEO and 404.

## Known limitations

- **Login rate limiting is per process and in memory.** Several Node processes multiply the allowed attempts. Move the counter to shared storage before scaling out.
- **No rate limit on theme upload, media upload, or preview token creation.** Only authenticated administrators can reach them, but a compromised admin account could fill the disk up to the per-request limits. Add a quota and a disk alarm.
- **CSP for the CMS pages is not set.** The admin uses Next.js inline scripts, which a strict CSP would need hashes or nonces for. Theme and media responses have their own CSP.
- **Sessions are not revoked on password change.** There is no change-password screen yet. Delete the user's `Session` rows manually if an account is compromised.
- **Uploaded images are not re-encoded.** A valid PNG or JPEG containing unusual metadata is stored as sent. Strip metadata in a later version.
- **Stylesheet validation is a deny-list.** Malicious CSS is limited by the forbidden constructs above and by the fact that a stylesheet cannot run code. CSS can still restyle the page, which is the purpose of themes.
- **The admin is for trusted operators.** A theme that is valid but ugly or inaccessible is not detected. Review uploads before activation.
- **Dependency advisories.** `npm audit` reports advisories in Next.js 15.x, Prisma 6.x and tailwindcss 3.x (see the deployment notes). Their fixes need major upgrades (Next 16, Prisma 7). Upgrade in a planned change and re-run the test suite.
